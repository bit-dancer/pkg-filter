## Обзор

Debian Package Filter Proxy — это HTTP-прокси сервер, который фильтрует метаданные Debian/Ubuntu репозиториев перед их передачей клиенту (например, Pulp). Приложение позволяет:
- Исключать пакеты по имени, версии или приоритету (например, `-dbg`, `-doc`, `-dev`).
- Оставлять только определенные версии пакетов (например, последние 3 версии или версии, соответствующие шаблону `6.2.*`).
- Автоматически разрешать зависимости, включая поиск в других репозиториях.
- Отдавать валидные файлы `Packages.gz` с корректными хешами и опциональной GPG подписью.
- Перенаправлять запросы к `.deb` файлам на оригинальный upstream (301 Redirect).

**Технологии**: Bun, TypeScript, SQLite. Никаких внешних npm зависимостей.

**Оптимизация для слабого железа**: Приложение спроектировано для работы на системах с ограниченными ресурсами (2 ядра, 1 Гб ОЗУ) при обработке больших объемов данных (20+ репозиториев по 60 тысяч пакетов).

**Версия**: 2.2.0

## Архитектура

### Компоненты системы

1. **HTTP сервер** (Bun.serve) — обрабатывает входящие запросы
2. **RepoManager** — управление репозиториями, синхронизация, работа с БД
3. **Filter** — применение правил фильтрации к пакетам
4. **Parser** — парсинг и сериализация Debian Packages файлов
5. **CacheManager** — кэширование Package файлов на диске
6. **SQLite** — хранение метаданных пакетов и зависимостей

### Поток данных

```
Клиент → HTTP запрос → Фильтрация → SQLite → Кэш → Ответ клиенту
                              ↓
                         Upstream (синхронизация)
```

## Логика фильтрации

Фильтрация применяется в следующем порядке:

1. **Include** — включение пакетов по правилам
2. **Exclude** — исключение пакетов по правилам
3. **Version Keep** — ограничение количества версий
4. **Dependency Resolution** — разрешение зависимостей

## API

### Эндпоинты

#### GET /health

Проверка здоровья сервиса.

**Ответ**:
```json
{
  "status": "ok",
  "timestamp": "2024-05-20T12:00:00.000Z"
}
```

#### GET /repos

Список всех настроенных репозиториев.

**Ответ**:
```json
[
  {
    "id": "ubuntu-noble",
    "config": {...},
    "packagesCount": 50000,
    "lastSync": "2024-05-20T11:00:00.000Z",
    "syncStatus": "success"
  }
]
```

#### GET /r/:repo/sync

Принудительная синхронизация репозитория.

**Ответ**:
```json
{
  "repoId": "ubuntu-noble",
  "success": true,
  "packagesCount": 60000,
  "filteredCount": 15000,
  "unresolvedDeps": [],
  "timestamp": "2024-05-20T12:00:00.000Z"
}
```

#### GET /r/:repo/packages/list

Список отфильтрованных пакетов с пагинацией.

**Параметры**:
- `limit` — количество пакетов (1-1000, по умолчанию 100)
- `offset` — смещение (по умолчанию 0)
- `name` — фильтр по имени пакета

**Ответ**:
```json
{
  "packages": [...],
  "total": 15000,
  "limit": 100,
  "offset": 0
}
```

#### GET /r/:repo/info

Информация о репозитории.

**Ответ**:
```json
{
  "config": {...},
  "packagesCount": 15000,
  "lastSync": "2024-05-20T11:00:00.000Z",
  "syncStatus": "success"
}
```

#### GET /r/:repo/logs

Логи синхронизации репозитория.

**Параметры**:
- `limit` — количество записей (по умолчанию 100)

**Ответ**:
```json
[
  {
    "id": 1,
    "repo_id": "ubuntu-noble",
    "timestamp": "2024-05-20T11:00:00.000Z",
    "level": "info",
    "message": "Sync completed"
  }
]
```

#### GET /r/:repo/dists/:dist/:component/binary-:arch/Packages(.gz)?

Отдача отфильтрованного файла Packages или Packages.gz.

#### GET /r/:repo/pool/*

Редирект (301) на оригинальные .deb пакеты upstream.

#### GET /metrics

Метрики системы.

**Ответ**:
```json
{
  "packages": 150000,
  "repositories": 5,
  "uptime": 86400.5,
  "httpRequests": {
    "successful": 1000,
    "failed": 5
  },
  "synchronization": {
    "ubuntu-noble": {
      "lastSync": "2024-05-20T11:00:00.000Z",
      "status": "success",
      "isSyncing": false,
      "duration": 120000,
      "packagesCount": 50000
    }
  }
}
```

**Поля метрик**:
- `packages` — общее количество пакетов во всех репозиториях
- `repositories` — количество настроенных репозиториев
- `uptime` — время работы программы в секундах
- `httpRequests.successful` — количество успешных HTTP запросов (статус < 500)
- `httpRequests.failed` — количество HTTP запросов с ошибками (статус ≥ 500)
- `synchronization` — информация о синхронизации по каждому репозиторию:
  - `lastSync` — время последней синхронизации
  - `status` — статус последней синхронизации (success/failed)
  - `isSyncing` — выполняется ли синхронизация в данный момент
  - `duration` — длительность последней синхронизации в миллисекундах
  - `packagesCount` — количество пакетов в репозитории

## Примеры использования

Подробные примеры конфигураций и фильтров доступны в документе [EXAMPLES.md](./EXAMPLES.md).

### Быстрый старт

1. Создайте файл `config.json`:
```json
{
  "ubuntu-noble": {
    "upstream": "http://ru.archive.ubuntu.com/ubuntu",
    "dist": "noble",
    "components": ["main"],
    "arch": ["amd64"],
    "exclude": [
      { "name": ".*-dbg$" },
      { "name": ".*-dev$" },
      { "name": ".*-doc$" }
    ],
    "allow-unresolved": true
  }
}
```

2. Запустите сервер:
```bash
bun run index.ts
```

3. Проверьте доступность:
```bash
curl http://localhost:8080/health
curl http://localhost:8080/metrics
```

## Метрики

Эндпоинт `/metrics` предоставляет информацию о состоянии системы:

### Основные метрики

- **Количество пакетов** — общее число пакетов во всех репозиториях
- **Количество репозиториев** — число настроенных репозиториев
- **Uptime** — время работы программы в секундах

### HTTP статистика

- **Успешные запросы** — количество запросов со статусом < 500
- **Запросы с ошибками** — количество запросов со статусом ≥ 500

### Информация о синхронизации

Для каждого репозитория доступна следующая информация:

- **lastSync** — дата и время последней синхронизации
- **status** — статус последней синхронизации (`success` или `failed`)
- **isSyncing** — флаг выполнения синхронизации в текущий момент
- **duration** — время затраченное на последнюю синхронизацию (в миллисекундах)
- **packagesCount** — количество пакетов в репозитории

### Пример запроса метрик

```bash
curl http://localhost:8080/metrics | jq .
```

## GPG подпись

Для подписи репозиториев используется утилита `gpg`.

### Настройка GPG

1. Установите GPG:
```bash
apt install gnupg
```

2. Создайте или импортируйте ключ:
```bash
gpg --gen-key
```

3. Укажите `gpgKey` в конфигурации репозитория.

## Устранение неполадок

### Проблема: Неразрешенные зависимости в логе

**Причина**: Зависимость не найдена в текущем репозитории.

**Решение**:
1. Добавьте репозиторий с системными пакетами в `deps-repos`.
2. Или установите `allow-unresolved: true`, если зависимости не критичны.

**Пример:**
```json
{
  "redis-noble": {
    "deps-repos": ["ubuntu-noble"],
    "allow-unresolved": false
  }
}
```

### Проблема: Пакеты не фильтруются

**Причина**: Некорректный RegExp паттерн.

**Решение**:
1. Проверьте паттерн на [regex101.com](https://regex101.com/).
2. Экранируйте специальные символы (например, `.` → `\\.`).
3. Используйте тестовый эндпоинт `/packages/list` для проверки.

### Проблема: Ошибка GPG подписи

**Причина**: Не установлен `gpg` или нет ключа.

**Решение**:
1. Установите `gpg`: `apt install gnupg`.
2. Импортируйте или создайте ключ: `gpg --gen-key`.
3. Укажите `gpgKey` в конфиге.

### Проблема: Медленная синхронизация

**Причина**: Большой размер репозитория или медленный upstream.

**Решение**:
1. Увеличьте `syncInterval` для редкой автоматической синхронизации.
2. Используйте более узкие фильтры для уменьшения количества пакетов.
3. Проверьте сетевое соединение с upstream.

## Производительность

Приложение оптимизировано для работы на слабом железе (2 ядра, 1 Гб ОЗУ) с большими объемами данных (20+ репозиториев по 60 тысяч пакетов).

### Архитектурные решения

#### SQLite для хранения метаданных
- **Таблица `packages_depends`** с индексами для быстрого поиска зависимостей
- **Статусы пакетов**: active, ignored, required, stale — для отслеживания состояния
- **Изоляция репозиториев**: уникальный ключ `(repo_id, package_name, version)`

#### Кэширование на диске
- Package файлы сохраняются в `data/cache/{repo_id}_{datetime}.{ext}`
- **Атомарная запись**: файлы записываются с префиксом `_`, после завершения синхронизации префикс убирается
- **Защита от битых файлов**: клиенты получают только завершенные файлы
- **Очистка старых версий**: хранится только N последних файлов и N часов

#### Потоковая обработка
- Обработка пакетов из upstream выполняется потоково, без загрузки всех данных в память
- Асинхронная синхронизация с кэшированием результатов

### Оптимизация алгоритмов

#### Разрешение зависимостей
- **До**: BFS в памяти — O(n) для пакетов с сотнями зависимостей
- **После**: SQL запросы с индексами — O(log n) благодаря индексам

#### Сортировка версий
- **До**: O(n log n) для каждого пакета с version-keep
- **После**: Быстрый поиск последней версии через индексированный запрос

### Рекомендации для слабого железа

1. **Увеличьте интервал синхронизации**: установите `syncInterval: 7200` (2 часа) или больше
2. **Используйте узкие фильтры**: уменьшайте количество обрабатываемых пакетов
3. **Отключите unnecessary функции**: `follow-recommends: false`, `follow-suggests: false`
4. **Мониторинг памяти**: следите за использованием ОЗУ через `htop` или аналоги

### Масштабирование

- **20 репозиториев × 60,000 пакетов** = 1.2 миллиона пакетов
- **Размер БД**: ~500 Мб с индексами
- **Время синхронизации**: 30-60 минут на репозиторий (зависит от upstream)
- **Использование памяти**: < 500 Мб благодаря потоковой обработке
