## Обзор

Debian Package Filter Proxy — это HTTP-прокси сервер, который фильтрует метаданные Debian/Ubuntu репозиториев перед их передачей клиенту (например, Pulp). Приложение позволяет:
- Исключать пакеты по имени, версии или приоритету (например, `-dbg`, `-doc`, `-dev`).
- Оставлять только определенные версии пакетов (например, последние 3 версии или версии, соответствующие шаблону `6.2.*`).
- Автоматически разрешать зависимости, включая поиск в других репозиториях.
- Отдавать валидные файлы `Packages.gz` с корректными хешами и опциональной GPG подписью.
- Перенаправлять запросы к `.deb` файлам на оригинальный upstream (301 Redirect).

**Технологии**: Bun, TypeScript, SQLite. Никаких внешних npm зависимостей.

**Оптимизация для слабого железа**: Приложение спроектировано для работы на системах с ограниченными ресурсами (2 ядра, 1 Гб ОЗУ) при обработке больших объемов данных (20+ репозиториев по 60 тысяч пакетов).

### Проблема: Неразрешенные зависимости в логе

**Причина**: Зависимость не найдена в текущем репозитории.

**Решение**:
1. Добавьте репозиторий с системными пакетами в `deps-repos`.
2. Или установите `allow-unresolved: true`, если зависимости не критичны.

**Пример:**
```json
{
  "id": "redis-noble",
  "deps-repos": ["ubuntu-noble"],
  "allow-unresolved": false
}
```

### Проблема: Пакеты не фильтруются

**Причина**: Некорректный RegExp паттерн.

**Решение**:
1. Проверьте паттерн на [regex101.com](https://regex101.com/).
2. Экранируйте специальные символы (например, `.` → `\\.`).
3. Используйте тестовый эндпоинт `/packages/list` для проверки.

### Проблема: Ошибка GPG подписи

**Причина**: Не установлен `gpg` или нет ключа.

**Решение**:
1. Установите `gpg`: `apt install gnupg`.
2. Импортируйте или создайте ключ: `gpg --gen-key`.
3. Укажите `gpgKey` в конфиге.

### Проблема: Медленная синхронизация

**Причина**: Большой размер репозитория или медленный upstream.

**Решение**:
1. Увеличьте `syncInterval` для редкой автоматической синхронизации.
2. Используйте более узкие фильтры для уменьшения количества пакетов.
3. Проверьте сетевое соединение с upstream.

## Производительность

Приложение оптимизировано для работы на слабом железе (2 ядра, 1 Гб ОЗУ) с большими объемами данных (20+ репозиториев по 60 тысяч пакетов).

### Архитектурные решения

#### SQLite для хранения метаданных
- **Таблица `packages_depends`** с индексами для быстрого поиска зависимостей
- **Статусы пакетов**: active, ignored, required, stale — для отслеживания состояния
- **Изоляция репозиториев**: уникальный ключ `(repo_id, package_name, version)`

#### Кэширование на диске
- Package файлы сохраняются в `data/cache/{repo_id}_{datetime}.{ext}`
- **Атомарная запись**: файлы записываются с префиксом `_`, после завершения синхронизации префикс убирается
- **Защита от битых файлов**: клиенты получают только завершенные файлы
- **Очистка старых версий**: хранится только N последних файлов и N часов

#### Потоковая обработка
- Обработка пакетов из upstream выполняется потоково, без загрузки всех данных в память
- Асинхронная синхронизация с кэшированием результатов

### Оптимизация алгоритмов

#### Разрешение зависимостей
- **До**: BFS в памяти — O(n) для пакетов с сотнями зависимостей
- **После**: SQL запросы с индексами — O(log n) благодаря индексам

#### Сортировка версий
- **До**: O(n log n) для каждого пакета с version-keep
- **После**: Быстрый поиск последней версии через индексированный запрос

### Рекомендации для слабого железа

1. **Увеличьте интервал синхронизации**: установите `syncInterval: 7200` (2 часа) или больше
2. **Используйте узкие фильтры**: уменьшайте количество обрабатываемых пакетов
3. **Отключите unnecessary функции**: `follow-recommends: false`, `follow-suggests: false`
4. **Мониторинг памяти**: следите за использованием ОЗУ через `htop` или аналоги

### Масштабирование

- **20 репозиториев × 60,000 пакетов** = 1.2 миллиона пакетов
- **Размер БД**: ~500 Мб с индексами
- **Время синхронизации**: 30-60 минут на репозиторий (зависит от upstream)
- **Использование памяти**: < 500 Мб благодаря потоковой обработке
